# 「衣服照片 → 搭配推荐」产品梳理

> 场景假设：**你自己一个人用**，你会写代码，先解决"衣柜里有什么、今天穿什么"，跑通后再考虑对外。
> 本文档的每个结论都按这个前提给，不按"做一家公司"的假设写。

---

## 0. 先说结论

| 维度 | 结论 |
|---|---|
| 形态 | **先做 PWA（手机浏览器加到桌面）**，不要一上来做小程序。理由见 §8.1 |
| MVP 规模 | 4 个页面：衣柜 / 拍照入库 / 今日搭配 / 穿着记录 |
| 核心算法 | **规则引擎筛 + 打分排序 + LLM 写理由**，不上虚拟试穿 |
| 技术栈 | Next.js + Supabase + 通义/Gemini 视觉模型 + Open-Meteo 天气 |
| 成本 | 自用规模 **< ¥10 / 月**，几乎全在免费额度内 |
| 开发量 | **4～6 周**（按每周 8～10 小时算），第 2 周就能开始真用 |
| 最大风险 | **不是技术，是录入成本**。录入超过 1.5 小时你一定会放弃 —— 这是全案第一约束 |

## 1. 需求本质：你到底在解决什么

"今天穿什么"这句话背后其实是三个不同的问题，别混在一起做：

| 真问题 | 症状 | 对应功能 |
|---|---|---|
| **看不见衣柜** | 常穿的就那 8 件，剩下 80 件在柜子深处吃灰 | 数字化 + 随机/被遗忘单品提醒 |
| **不会搭** | 站在柜子前发呆 5 分钟，最后穿回老一套 | 搭配推荐 + 给理由 |
| **记不住** | 上周穿过的忘了，照片里重复出镜 | 穿着日志 + 去重 |

第三个最容易被忽略，但它恰恰是**留存的关键**：一个只推荐、不记录的 App，用两周就会腻；一个记得你穿过什么的 App，用一年会越来越准。

还有两个"隐形场景"值得顺手覆盖，成本很低：

- **换季收纳**：清单式看"这件夏天还没穿过"，决定留/扔/送。
- **购物前**：想买一条卡其裤，先查"能不能和我现有的 12 件搭上"。这一条对自用极实用，直接抑制冲动消费。

## 2. 用户场景（就你一个人）

**早 7:40，赶时间**
打开 → 定位自动拿天气（18°C 阴）→ 默认"上班"场合 → 直接给 3 套 → 点"就这套" → 记入今天穿着。

**周日晚，整理**
挑 10 件平铺拍照 → 批量上传 → 自动打标签 → 逐个确认/改错 → 入库。一轮 15 分钟。

**周六，逛街前**
想买外套 → 搜索"外套" → 看现有 4 件和"最近 30 天穿着次数" → 决定不买 / 买。

**换季**
按"本季一次都没穿"筛选 → 一键标记"收起来"。

## 3. 产品主张与三条铁律

> **一句话：打开就是今天的三套，并且它知道你上周穿过什么。**

铁律（每一条都是踩过的坑）：

1. **录入必须 < 90 分钟完成 100 件。** 否则产品从第一天就死了。
2. **推荐必须给理由。** 不是"这套好看"，而是"藏青 + 米白同属低饱和中性色，配卡其裤形成三层明度差；18°C 加一件薄针织刚好"。
3. **必须记得穿过什么。** 没有记忆的推荐 = 每天抽奖。

## 4. 功能范围（MoSCoW）

### ✅ MVP（必须有，缺一个就跑不通）

- 拍照 / 相册批量上传，客户端压缩
- 自动打标签（类别、颜色、材质、风格、季节、正式度、保暖度）+ 人工确认
- 衣柜列表 + 按类别筛选
- 今日搭配：输入天气（自动）/ 场合 → 输出 3 套 + 理由
- 一键"今天穿这套" → 写入穿着记录
- 单品编辑 / 删除

### 🔵 V1（跑通两周后再加）

- 穿着记录页 + 日历视图
- "最近 30 天没穿"筛选
- 搭配收藏夹（手动拼一套存起来）
- 反馈：👍/👎 单套搭配，影响下次权重
- 离线可用（PWA Service Worker + IndexedDB 缓存）

### 🟡 V2（锦上添花）

- 行李箱模式：出差 3 天，生成 3 套 + 复用单品
- 购物决策：输入想买的单品属性，算"能和几件现有单品搭配"
- 颜色分析：你衣柜的主色调报告（顺带发现"全是黑白灰"）
- 体型参数（身高/肩宽/梨形苹果形）→ 版型建议

### ❌ 明确不做（省下 80% 的坑）

| 不做 | 原因 |
|---|---|
| **AI 虚拟试穿（人穿上这套衣服）** | 生成质量不稳定、单次成本高、对"今天穿什么"这个决策**没有增量价值**。这正是大多数同类产品烧钱死掉的地方 |
| 3D 体型建模 / 数字人 | 投入产出比极低 |
| 社交 / 社区 / 穿搭广场 | 你自用不需要，且是内容运营活儿 |
| 电商带货、同款链接 | 涉及类目资质 + 供应链，和自用目标冲突 |
| 全自动高精度抠图 | 允许不抠图也能用，抠图只做锦上添花 |

> 一句话：**这个产品的价值在"决策"，不在"成像"。** 别被 AI 试穿的 Demo 骗了。

## 5. 主流程

### 5.1 入库流程

```
拍照(平铺/挂拍) 
  → 客户端压缩到长边 1600px, WebP
  → 上传到 Supabase Storage，拿到 public URL
  → 后台异步：调视觉模型 → 返回 JSON 标签
  → 确认页（预填好，你只改错的）
  → 写 items 表
```

关键：**上传后立刻可以进下一个，打标签在后台跑**。不要让用户等模型。

### 5.2 推荐流程

```
定位 → Open-Meteo 拿体感温度/降水
场合（默认按星期几 + 时间猜，可切）
        ↓
① 硬过滤：季节、温度区间、正式度区间、被标记"收起来"的
        ↓
② 枚举组合：上装 × 下装 × 外套 × 鞋（戴口罩量级 < 1000 组）
        ↓
③ 打分排序 → Top 5
        ↓
④ LLM 精排 + 生成中文理由 → 输出 3 套
        ↓
⑤ 用户选一套 → 写 wear_logs → 更新单品 times_worn / last_worn
```

## 7. 推荐算法：三层，别上深度模型

### 7.1 为什么不用向量检索

自用规模是 **50～200 件**。这个量级下：

- 组合总数 = 上装 8 × 下装 6 × 外套 4 × 鞋 4 = **768 组**，全枚举打分只要几毫秒。
- 向量相似度解决的是"从十万件里找相似"，你根本用不上。
- 结构化属性 + 规则**可解释、可调参、出错能马上改**，比一个黑盒 embedding 好用得多。

**结论：写规则，别训练模型。** 把 LLM 用在它真正擅长的地方——理解语境、写理由、处理"今天见客户但要搬东西"这种规则表达不了的软约束。

### 7.2 硬过滤（不做这一步，后面全是噪音）

```python
def hard_filter(items, temp, occasion_season, formality_target):
    need_warmth = warmth_target(temp)   # 见 7.4
    return [i for i in items
            if i.status == 'active'
            and occasion_season in i.season
            and abs(i.formality - formality_target) <= 1
            and abs(i.warmth - need_warmth) <= 2]
```

### 7.3 打分（0～1 加权）

```
total = 0.30 * 场合匹配
      + 0.25 * 颜色和谐
      + 0.20 * 温度匹配
      + 0.15 * 新鲜度
      + 0.10 * 个人偏好
```

| 分项 | 算法 |
|---|---|
| **场合匹配** | `1 - abs(avg_formality - target)/4`，再与 style_tags 目标场合的 Jaccard 取平均 |
| **颜色和谐** | 见 7.5 |
| **温度匹配** | `1 - abs(整套 warmth - 目标 warmth)/4` |
| **新鲜度** | 任一件近 3 天穿过 → 扣 0.3；整套与近 14 天重复 → 扣 0.5；30 天没穿的加分 |
| **个人偏好** | 该单品历史 rating 均值归一化，无数据时 0.5 |

### 7.4 保暖度合成与温度映射

```
整套 warmth = 0.4*上装 + 0.4*下装 + 0.7*外套 + 0.15*鞋
```

| 体感温度 | 目标 warmth |
|---|---|
| ≥ 28°C | 1.5 |
| 22～28°C | 2.0 |
| 16～22°C | 2.8 |
| 10～16°C | 3.6 |
| 4～10°C | 4.3 |
| < 4°C | 5.0 |

（降雨 > 50% → 鞋类只保留防水/皮革，这条规则一条就够）

### 7.5 颜色和谐（90% 的效果在这一条）

用 HSL 算，不用 RGB。

```
1. 若整套里中性色（黑/白/灰/米/藏青）占比 ≥ 2/3 → 基础分 0.85
2. 同色系（色相差 ≤ 30° 且明度差 ≥ 15%）→ 0.90（最高分，因为最稳）
3. 邻近色（色相差 30～60°）→ 0.80
4. 互补/三角（120～180°）→ 0.65，但若其中一件是"点缀面积小"（包/鞋/配饰）→ 0.85
5. 高饱和单品（S > 0.6）出现在 ≥ 2 件 → 强制扣到 0.4
6. 花纹 + 花纹 同时出现在上装和下装 → 扣 0.25
```

### 7.6 LLM 精排（把 Top 5 变 3 套 + 写理由）

Prompt 骨架：

```
你是我的私人搭配师。今天是 11 月 5 日周三，上海，阴，体感 18°C。
场合：上班（需见客户，正式度 4）。

我的候选搭配（已按规则打分）：
1. [藏青针织衫(formality 4,warmth 3) + 卡其西裤(4,3) + 米白风衣(4,3) + 深棕乐福鞋(4,2)]
2. ...
（共 5 套，含单品属性）

请：
- 从中选 3 套，按"今天最合适"排序
- 每套给一句 30 字以内的中文理由，说明为什么适合今天的天气和场合
- 指出如果有更优的手动组合，用我现有的单品

只输出 JSON：{"outfits":[{"rank":1,"item_indices":[...],"title":"...","reason":"..."}]}
```

Token 消耗：5 套 × 4 件 × 十几个字段，约 1500 token 输入、300 输出。**每次推荐约 ¥0.002**。一天点 5 次，一个月 3 毛钱。

### 7.7 数据飞轮

穿完第二天补一个评分 → `wear_logs.rating` → 单品偏好分 → 影响下次排序。
三周后，推荐会明显贴合你。**这是唯一需要坚持做的事**。

## 8. 技术选型

### 8.1 形态对比：为什么推荐 PWA

| | PWA / H5 | 微信小程序 | 原生 App |
|---|---|---|---|
| 上手时间 | **当天** | 注册 + 认证 + ICP 备案 + 审核，1～2 周 | 上架审核 + 开发者账号 |
| 改一版 | 推一次代码，10 秒 | 重新提审，1～3 天 | 重新提审，1～3 天 |
| 拍照 | `<input capture>` 可用 | 体验最好 | 最好 |
| 手机桌面 | 添加到主屏幕，图标一样用 | 微信内 | 原生 |
| 自用合适度 | ★★★★★ | ★★★☆（流程成本高） | ★★ |
| 分享给朋友 | 发链接 | 最顺 | 麻烦 |

**建议路径：PWA 打通闭环 → 真用 3 周 → 如果确认有价值且想分享，再用同一套后端搬小程序（Taro/uni-app 或直接重写页面，数据结构不用动）。**

反过来（先做小程序）的风险是：备案审核那两周你会失去所有动力，而且第一次做必然会大改，改一次等三天。

### 8.2 推荐技术栈

```
前端   Next.js 15 (App Router) + TypeScript + Tailwind + shadcn/ui
       PWA: manifest + Service Worker（离线缓存衣柜）
数据   Supabase：Postgres + Storage + Auth（magic link，免密码）
       —— 免费额度：500MB 数据库 / 1GB 存储，自用绰绰有余
视觉   通义 qwen-vl-max（阿里云百炼，国内直连、有免费额度）
       备选：Gemini 2.0 Flash（更便宜，需代理）
抠图   @imgly/background-removal（浏览器端 WASM，免费、离线、不上传）
       —— 质量不够再换 remove.bg / Photoroom API（~¥0.15/张）
天气   Open-Meteo（免费、无需 API Key、支持按经纬度取体感温度）
部署   Vercel（免费）或 Cloudflare Pages
```

| 每次推荐 | ¥0.002 |

## 9. 入库体验：全案最容易被低估的部分

**现实中 90% 的衣柜 App 死于"用户不愿意录入"。** 这一节比算法重要。

### 9.1 拍摄规范（贴在墙上那种）

- 平铺在白床单 / 白墙前，**纯色底 + 顶光/自然光**，不要黄光（会毁掉颜色识别）。
- 一件一张，正对拍，占画面 70%。
- iPhone 用户可直接"长按照片主体"导出抠好的 PNG，效果比任何 API 都好，还是免费的。

### 9.2 降摩擦的三个设计

1. **批量上传 + 后台打标**：选 20 张 → 一次性传 → 去喝杯水 → 回来确认。
2. **确认页只改错的**：预填好所有字段，错误的点一下，不要做"填写表单"。
3. **允许"先存后用"**：只有类别和颜色是必填，其余空着也能先入库，用的时候再补。

### 9.3 视觉模型 Prompt（可直接用）

```
你是一个服装属性标注器。看这张衣服照片，输出严格 JSON，不要任何解释：

{
  "category": "upper|lower|outer|dress|shoes|bag|accessory",
  "subcategory": "中文，如 针织衫/西裤/乐福鞋",
  "color_name": "中文色名，如 藏青/燕麦色",
  "color_hex": "#RRGGBB，取占面积最大的主色",
  "secondary_colors": ["#RRGGBB"],
  "pattern": "solid|stripe|check|floral|graphic|other",
  "material": "棉|羊毛|真丝|牛仔|皮革|化纤|针织",
  "style_tags": ["从 通勤/休闲/运动/复古/极简/法式/街头 中选1-3个"],
  "season": ["春","夏","秋","冬"],
  "formality": 1-5 的整数,
  "warmth": 1-5 的整数,
  "fit": "修身|常规|宽松",
  "confidence": 0.0-1.0
}
```

配 few-shot 两三个例子，准确率能到 85% 以上。剩下 15% 手动改，改一次只要 3 秒。

## 10. 里程碑（每周 8～10 小时）

| 周 | 目标 | 验收标准 |
|---|---|---|
| **W1** | 骨架：Supabase 建表 + 拍照上传 + 衣柜列表 + 手动打标 | 能存进 20 件并看到网格 |
| **W2** | 视觉打标 + 确认页 + 抠图 + 批量上传 | 录入 20 件 ≤ 8 分钟，自动标签准确率 > 80% |
| **W3** | 规则引擎 + 今日搭配页（先不做 LLM） | 输入温度和场合，出 3 套，理由用模板拼 |
| **W4** | LLM 精排 + 理由生成 + 一键"就这套" + 穿着记录 | **可以开始每天真用了** |
| **W5** | 天气自动获取 + 场合预设 + 新鲜度加权 + PWA 离线 | 早上 10 秒内拿到结果 |
| **W6** | 反馈 + 收藏 + "30 天未穿"筛选；然后**停止开发**，真用两周 | 两周内至少用了 10 天 |

> W4 结束就该开始自己用了。**不要等到功能全了再用**，否则你会在第 6 周发现方向错了。

## 11. 风险清单

| 风险 | 概率 | 应对 |
|---|---|---|
| **录入太累，直接放弃** | 高 | 只录 30 件最常穿的就能跑通；拍摄规范化；批量 + 后台打标 |
| 单品太少，搭配质量差（冷启动） | 高 | 少于 15 件时只做"单品推荐"，不硬凑整套 |
| 黄光下颜色识别偏 | 中 | 拍的时候用白纸做参考；允许手动取色；主色只取 HSV 面积最大 |
| 抠图对毛绒/透明材质效果差 | 中 | 允许不抠，原图卡片照样好看；iPhone 长按抠图兜底 |
| 推荐越来越"抽奖" | 中 | 必须做新鲜度惩罚 + 穿着日志，否则每天都是同一套 |
| 自用产品变成"数据录入地狱" | 中 | 允许脏数据：必填只有类别 + 颜色 |
| 熬夜做 3 个月然后不用了 | 中 | 4 周出可用版，先验证"你会不会天天打开"再投入 |

## 12. 下一步

**建议的下一步是：先花一个周末做 W1 的骨架，存 30 件衣服进去，然后你自己试试"看着这 30 件，你想要它给你什么"。** 拿着这个真实感受再回来定功能，比现在拍脑袋准得多。

需要我接下来帮你做的话，可以直接说：

1. **搭 MVP 骨架** — Next.js + Supabase，含建表 SQL、拍照上传、衣柜列表
2. **写推荐引擎** — 颜色和谐 + 打分 + 组合枚举，纯函数，可单测
3. **写视觉打标模块** — qwen-vl / Gemini 的调用封装 + JSON 校验 + 降级
4. **做小程序版本** — 如果你确实想走小程序 + 云开发

原先挂着的三个点已经定了：

- **数据放哪** → **Supabase 免费云**。手机随时用，换设备数据还在；代价是照片在云上。
- **场合怎么定** → **按"星期几 + 时间"自动猜**（周六日→休闲，周五 18 点后→约会，其余→上班），顶部点一下就改。
- **要不要记录价格** → **不记**。每次穿着成本是好指标，但要先输价格，而这是入库时最容易被放弃的一步。少一个字段，录 100 件的心理成本低很多。
